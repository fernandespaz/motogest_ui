Perfis de acesso

O protótipo assume 4 papéis fixos. O backend real não tem papéis fixos — tem um perfil (nome livre) com um conjunto de códigos de permissão. A tabela abaixo traduz um modelo para o outro.

Papel do protótipoTradução no backend realMódulos
Root Não é um perfil de tenant — é o X-Admin-Token da plataforma, já implementado no Console do Root (/root/oficinas), fora do app de tenant. Cadastro de oficinas, visão de todas as licenças
Admin Preset de perfil ADMIN (já existe em perfilPresets.ts) = todos os códigos de permissão do catálogo Todos os módulos do tenant
Mecânico Novo preset — só ORDEM_SERVICO_READ/WRITE, CHECKLIST_WRITE, FOTO_WRITE Ordens de Serviço (visão restrita) + Agenda de leitura
Consultor Técnico Já existe (CONSULTOR em perfilPresets.ts) — ajustar para garantir ESTOQUE_READ, CLIENTE_*, VEICULO_*, ORCAMENTO_WRITE Estoque (leitura), Clientes, Veículos, Orçamentos + envio por WhatsApp (já implementado)
⚠ Ponto de atenção

"Root" no protótipo aparece como mais um item de um seletor de papéis dentro do mesmo app — na arquitetura real ele é propositalmente um sistema separado (token de plataforma, nunca exposto no bundle público). Não dá pra tratar Root como um perfil comum sem reabrir a discussão de segurança já resolvida com vocês.

Layout diferenciado por perfil

O protótipo tem dois "shells" completamente diferentes: um desktop (sidebar + topbar + Kanban) para Admin, e um app de cartões com bottom nav para o Mecânico. Hoje o MotoGest real tem um único shell responsivo (sidebar que vira bottom nav) para todos os perfis.

Admin / Root — desktop-first

Mantém o AppShell atual (sidebar fixa + topbar), só re-estilizado com os novos tokens. Ganha visão Kanban opcional nas Ordens de Serviço.

Sidebar 242px Topbar + busca
Mecânico / Consultor — mobile-first

Shell novo (OperatorShell): topo escuro fixo, abas "Aguardando início / Em andamento", cartões grandes de OS, bottom nav de 3 itens.

Cartões touch-friendly Bottom nav

Na arquitetura MVVM já adotada, isso é só uma segunda View — o Model (api/) e o ViewModel (hooks/) continuam únicos e reaproveitados por ambos os shells. Qual shell renderizar é decidido por hasPermission(), do mesmo jeito que hoje decidimos o que aparece no menu.

Componentes novos a construir

  • Kanban de Ordens de Serviço — uma coluna por status (hoje é só tabela), com cartão compacto (placa, veículo, mecânico). Visão desktop, alternável com a tabela atual.
  • Stepper de status — trilha horizontal de status clicáveis (substitui o Select de status atual no admin; no Mecânico vira uma versão restrita, só com os status operacionais).
  • OS Card (mobile) — cartão de OS estilo "ticket" para o shell do Mecânico, com reclamação do cliente, previsão e botão de ação primária.
  • Categorias de estoque em cards — filtro visual por categoria (Lubrificantes/Peças/Filtros) antes da tabela, com contagem de itens críticos.
  • Login split-screen — painel de marca (esquerda) + formulário (direita), com fallback de ilustração SVG quando a oficina não tem imagem cadastrada.

Gaps de backend identificados

  • Upload real de imagem por tenant — hoje só existe logoUrl (string ≤500 caracteres) em OficinaUpdateRequest. Não há endpoint de upload multipart nem armazenamento de arquivo. Sem isso, "imagem da loja enviada pelo cliente" continua sendo, na prática, colar uma URL já hospedada em outro lugar.
  • Branding pré-login — não existe (nem faria sentido existir) um endpoint público que devolva nome/logo da oficina a partir do identificador antes da autenticação, sem abrir uma brecha de enumeração de tenants. Login mostra a marca da oficina só depois de autenticar.

Decisões pendentes antes de implementar

Para não construir a tela duas vezes, preciso da sua confirmação nestes pontos:

  • Reskin completo de cores/tipografia agora, ou manter o indigo atual e só aplicar a paleta nova nas telas novas (Login, OperatorShell)?
  • "Nome fantasia no login" fica só pós-autenticação (como já é), ou vale investir num fluxo de 2 passos (identificador → mostra marca → senha) mesmo sabendo o custo de contrato de API?
  • Shell separado para Mecânico/Consultor (mobile-first, como o protótipo) ou continuar com um único shell responsivo, só priorizando os itens certos no bottom nav (como já fizemos antes)?
  • Preset "Mecânico" deve ser só um ponto de partida editável (como os outros presets hoje) ou uma trava rígida de permissões?
  • Kanban de OS é uma visão alternativa (com toggle) ou substitui a tabela atual?
